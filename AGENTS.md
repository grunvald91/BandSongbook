# AI-агент: Band Book

Этот репозиторий содержит Android-клиент, sync-server и общий канонический слой `PRODUCT.md`, `ARCHITECTURE.md`, `RULES.md`, `ROADMAP.md`. Web/PWA находится в отдельном `BandBook-v2`; его локальные инструкции могут описывать только Web-специфику и не переопределяют общий слой.

## Два типа истины и явный конфликт

- **CURRENT STATE** — как система фактически работает в указанной рабочей копии или среде. Источники: production и фактическая конфигурация (только при прямой проверке), рабочий код, Git-состояние, результаты тестирования. Не выводи состояние production из Git и не называй код без проверки стабильным.
- **INTENDED STATE** — как система должна работать по актуальным явным решениям владельца и утверждённым `PRODUCT.md`/`RULES.md`. Код или production не могут автоматически менять требования только потому, что сейчас устроены иначе. Наличие требования в документах не доказывает его реализацию.
- Если CURRENT STATE и INTENDED STATE расходятся, запиши **IMPLEMENTATION GAP**: требование, проверенный фактический результат, версии/среда, последствия и необходимая проверка или решение. Если факт не проверен, так и напиши; отсутствие проверки не равно установленному gap.
- Найденное агентом предполагаемое правило до решения владельца обозначай **CANDIDATE INVARIANT**. Не объявляй его утверждённым на основании комментария, теста или исторического плана.

При споре о *факте* проверяй соответствующую текущую копию и среду; при споре о *норме* опирайся на утверждённое решение владельца. README, исторические спецификации/планы, сообщения и память дают контекст, но не переопределяют эти две категории. Явно сообщай владельцу о противоречии документов.

## Перед изменением

1. Определи репозиторий, ветку, HEAD, `git status --short --branch --untracked-files=all` и затронутый рабочий diff. Учитывай untracked файлы; старый `master` не подменяет нынешнюю Android working copy.
2. Прочти этот слой, точку входа, относящиеся модели/экран/контракт, тесты и конфигурацию. Для sync-изменений проверь Android + Web + server, старые клиенты, неизвестные поля, удаления/воскрешение, timestamps, личные настройки, очередь и срок жизни аудио-URL.
3. Уточни границы поручения. Владелец накапливает правки BandSongbook; не применяй их до отдельной команды начать. Исторические checkbox-планы и существование fix-ветки не являются разрешением работать или сливать.
4. Не раскрывай секреты из исходников в чате, diff-резюме или логах.

## Работа с незакоммиченным и контроль владельца

Android working copy — WORKING и кандидат на следующую версию, не STABLE. Прежде чем сохранять её checkpoint-коммитом/веткой, **покажи владельцу Git status, исключения временных файлов/секретов/мусора и краткое резюме diff**; дождись решения о составе и checkpoint. Не делай `stash`, `reset`, `clean`, `checkout`, rebase или коммит чужих изменений по умолчанию. Не запускай тесты или сборку, если поручение строго read-only: они могут создавать файлы.

Явного отдельного решения владельца требуют: применение накопленных правок; выбор конфликтного алгоритма и модели прав; конкретный merge fix-ветки; публикация, APK-релиз, деплой, production-конфигурация, ротация/использование секретов, миграция или перезапись БД, удаление данных, откат/восстановление с побочными эффектами. Для Web базой сейчас является `feature/prod`; отдельные ветки проверяй относительно неё и Android sync-контракта, но не сливай автоматически.

## Проверка и документация

Для разрешённого изменения подбирай целевые тесты, затем релевантные общие тесты, lint/typecheck и сборку; UI проверяй на экране/устройстве, sync — конфликтными межклиентскими сценариями включая старый клиент, деплой — readback и проверкой фактической среды. Приводи команды, результаты и ограничения; не присваивай STABLE до выполнения критериев из `ROADMAP.md` и признания владельцем. DEPLOYED подтверждается отдельно для каждой среды.

После утверждённого изменения назначения обнови `PRODUCT.md`, границ системы — `ARCHITECTURE.md`, инварианта — `RULES.md`, состояния/следующего решения — `ROADMAP.md`, процесса работы — `AGENTS.md`. Обновляй CURRENT STATE по доказательствам, INTENDED STATE — только по решениям владельца; сохрани видимый IMPLEMENTATION GAP до его проверки и закрытия. Не переписывай исторические планы задним числом. Web-репозиторий ссылается на эти документы, а не ведёт их независимую копию.

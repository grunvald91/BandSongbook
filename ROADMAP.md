# Band Book — состояние и ближайшие решения

Это не старый план с незакрытыми чекбоксами. **CURRENT STATE** — проверенные исходники и отдельно проверенная среда; **INTENDED STATE** — решения владельца; **IMPLEMENTATION GAP** — доказанное расхождение. Статус кода не определяет продуктовые требования.

## Статусы версий

- **WORKING** — текущая незавершённая работа.
- **CANDIDATE** — сохранённая версия, которую владелец тестирует; не равна stable/release.
- **STABLE** — признанная владельцем рабочей версия: сохранена в Git, собирается, основные сценарии работают, релевантные проверки пройдены, нет известной критической причины откатить и есть понятная точка возврата.
- **DEPLOYED** — версия, фактически опубликованная на конкретной среде; устанавливается проверкой этой среды, не по Git. STABLE и DEPLOYED — разные оси, не последовательные ярлыки.

Ни одному клиенту здесь не присваивается STABLE или DEPLOYED только по наличию исходников.

## CURRENT STATE

- Android `master` — старый закоммиченный baseline. Текущая Android working copy с изменёнными и новыми файлами — **WORKING**, кандидат на следующую версию, **не подтверждённая STABLE и пока не безопасно сохранённая checkpoint-точка Git**.
- Web/PWA `feature/prod` — текущая базовая ветка. Неслитые security/playback, tombstone/merge и другие ветки не становятся частью неё автоматически.
- В исходниках есть Android-клиент, Web/PWA и FastAPI sync-server; фактически запущенные версии, auth/storage, БД и backup не подтверждены. Проверка публичной страницы сама по себе не подтверждает весь API.
- Старые `README.md` и `BandBook-v2/docs/superpowers/plans/` частично устарели; их пункты не являются автоматически активными задачами.

## INTENDED STATE — утверждённые направления

- Требования продукта и UX — `PRODUCT.md`; межклиентские инварианты — `RULES.md`.
- Синхронизация должна сохранять изоляцию групп, tombstone, неизвестные поля и личные настройки, не превращая signed URL в постоянные данные; конфликтный алгоритм должен быть предсказуемым.
- Модель owner/admin пока **не утверждена**; выбор прав после просмотра фактических прав и вариантов.
- Приоритет безопасности и эксплуатации — высокий, но production и секреты не менять без отдельного разрешения.

## IMPLEMENTATION GAPS и непроверенное

- **Риск расхождения:** Android LWW/tombstone и нынешние Web full-snapshot push/серверная замена не доказаны совместимыми с intended state; конкретные сценарии потери/воскрешения требуют review и тестов, а не догадки о стабильности.
- **Не подтверждено:** соблюдение всех UX-инвариантов на обеих платформах и на устройстве; действующие права участников, auth, объектное хранилище, backup, опубликованные версии, update API и recovery.
- **Установленный документальный пробел:** нет согласованного backup/restore/rollback runbook для сервера, БД, аудио и клиентов.
- **Установленный security-риск в исходниках:** секреты присутствуют в скриптах веб-деплоя; действительность значений ещё не подтверждена. Не выводить их в отчётах.
- Веб-рендер HTML требует проверки санитизации; отдельная fix-ветка не доказывает исправления в `feature/prod`.

## Следующие действия и ворота

1. **Android checkpoint:** перед любым коммитом показать владельцу `git status`, список исключаемого мусора/секретов и краткий diff; только затем, по отдельному решению, сохранить безопасную checkpoint-ветку/коммит. Не помечать release или STABLE.
2. **Security:** определить действительность секретов без их раскрытия; считать опубликованные в Git потенциально скомпрометированными, подготовить план ротации и безопасной конфигурации, проверить HTML/sanitization. Ротация и production-изменения — только после отдельного разрешения.
3. **Sync review:** сопоставить текущие Android, Web `feature/prod` и сервер, старых клиентов, удаления, воскрешение, одновременную запись и сохранение неизвестных полей; предложить конкретный алгоритм и тесты владельцу.
4. **Web fixes:** оценить каждую отдельную ветку относительно `feature/prod` и актуального Android-контракта; предложить конкретный merge, ничего автоматически не сливая.
5. **Эксплуатация:** после security-review подготовить проверяемый backup/restore/rollback runbook и подтвердить фактические deployed версии и конфигурацию без самовольных изменений.

Это последовательность изучения и решений, а не разрешение выполнять перечисленные изменения. Обновлять статусы только по свежим свидетельствам и решениям владельца.
